# Асинхронный сервис процессинга платежей — проектное решение

Документ фиксирует архитектуру, принятые решения и их обоснование. Он написан
до кода и служит источником правды для реализации.

## 1. Контекст

Сервис принимает запросы на оплату по HTTP, обрабатывает их асинхронно через
эмуляцию внешнего платёжного шлюза и уведомляет клиента о результате через
webhook.

Ключевое свойство системы: **приём платежа и его обработка разнесены во
времени**. HTTP-запрос завершается в момент, когда платёж надёжно сохранён и
поставлен в очередь на обработку (`202 Accepted`), а не когда шлюз вернул
результат.

Из этого следуют три требования, вокруг которых построен весь дизайн:

1. **Ни один принятый платёж не должен потеряться** между БД и брокером →
   Outbox pattern.
2. **Повторный HTTP-запрос не должен создать второй платёж** → Idempotency key.
3. **Повторная доставка сообщения из брокера не должна привести к повторному
   списанию** → идемпотентный consumer.

## 2. Модель данных

### 2.1 `payments`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | `uuid` PK | Идентификатор платежа |
| `idempotency_key` | `text` UNIQUE NOT NULL | Защита от дублей на входе |
| `request_fingerprint` | `char(64)` NOT NULL | SHA-256 канонизированного тела запроса |
| `amount` | `numeric(18,2)` NOT NULL | Сумма, `CHECK (amount > 0)` |
| `currency` | `currency` (native enum) | `RUB`, `USD`, `EUR` |
| `description` | `text` NOT NULL | Описание платежа |
| `metadata` | `jsonb` NOT NULL DEFAULT `'{}'` | Произвольные данные клиента |
| `status` | `payment_status` (native enum) | `pending`, `succeeded`, `failed` |
| `failure_reason` | `text` NULL | Причина отказа шлюза |
| `webhook_url` | `text` NULL | Куда уведомлять |
| `webhook_attempts` | `int` NOT NULL DEFAULT 0 | Счётчик попыток доставки |
| `webhook_delivered_at` | `timestamptz` NULL | Момент успешной доставки |
| `webhook_last_error` | `text` NULL | Диагностика последней неудачи |
| `created_at` | `timestamptz` NOT NULL | Момент приёма |
| `updated_at` | `timestamptz` NOT NULL | Обновляется триггером ORM |
| `processed_at` | `timestamptz` NULL | Момент получения ответа шлюза |

`amount` — `numeric`, а не `float`: деньги нельзя хранить в двоичной плавающей
точке. В JSON сумма сериализуется строкой (`"100.50"`) по той же причине.

Колонка называется `metadata`, но атрибут модели — `payment_metadata`:
`metadata` зарезервировано в SQLAlchemy Declarative.

### 2.2 `outbox_messages`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | `uuid` PK | Он же `message_id` в брокере (дедупликация) |
| `aggregate_type` / `aggregate_id` | `text` / `uuid` | Кого касается событие |
| `event_type` | `text` | `payment.created` |
| `routing_key` | `text` | `payments.new` |
| `payload` | `jsonb` | Тело события |
| `created_at` | `timestamptz` | Порядок публикации |
| `published_at` | `timestamptz` NULL | NULL = не опубликовано |
| `attempts` | `int` | Счётчик неудачных публикаций |
| `next_retry_at` | `timestamptz` | Backoff при недоступности брокера |
| `last_error` | `text` NULL | Диагностика |

Частичный индекс `WHERE published_at IS NULL` — таблица растёт, а сканировать
нужно только неопубликованный хвост.

## 3. Outbox pattern

Проблема, которую он решает: нельзя атомарно записать в PostgreSQL и
опубликовать в RabbitMQ. Если писать в БД, а потом публиковать, то падение
между этими шагами теряет событие; если публиковать первым — событие может
ссылаться на несуществующий платёж.

Решение: **API пишет платёж и запись в `outbox_messages` одной транзакцией**.
Отдельный процесс `relay` читает неопубликованные записи и публикует их.

```
POST /payments ──► BEGIN
                     INSERT INTO payments ...
                     INSERT INTO outbox_messages ...
                   COMMIT               ──► 202 Accepted
                        │
   relay (каждые 200мс) │
        SELECT ... WHERE published_at IS NULL
               ORDER BY created_at
               FOR UPDATE SKIP LOCKED LIMIT 50
                        │
                   publish (persistent, confirms, message_id=outbox.id)
                        │
                   UPDATE published_at = now()
                        │
                     COMMIT
```

`FOR UPDATE SKIP LOCKED` позволяет запускать несколько реплик relay без
двойной публикации и без блокировок между ними.

**Гарантия — at-least-once, не exactly-once.** Если брокер подтвердил приём, а
`COMMIT` не прошёл, сообщение опубликуется повторно. Это осознанный выбор:
exactly-once между двумя системами недостижим без распределённой транзакции.
Дубликат гасится идемпотентностью consumer'а (§6), а `message_id = outbox.id`
даёт брокеру и потребителю стабильный ключ дедупликации.

Публикация идёт с **publisher confirms** (`mandatory=True` + подтверждение
брокера): без них `publish` — это запись в сокет, а не доставка, и потеря
сообщения при падении узла проходит незамеченной.

## 4. Топология RabbitMQ

Три обменника, пять очередей. Задержки ретраев реализованы очередями с TTL и
dead-letter-маршрутизацией, а не `asyncio.sleep` внутри воркера: спящий воркер
занимает слот prefetch и умирает вместе с задержкой при рестарте.

```
                    ┌──────────────────────┐
   relay ─────────► │ exchange: payments   │ (direct, durable)
                    └──────────┬───────────┘
                     rk: payments.new
                               ▼
                    ┌──────────────────────┐
                    │ queue: payments.new  │ ◄── consumer
                    └──────────────────────┘
                               │ ошибка обработки, attempt < 3
                               ▼
                    ┌──────────────────────────┐
                    │ exchange: payments.retry │ (direct, durable)
                    └──────────┬───────────────┘
                rk: retry.1 / retry.2 / retry.3
                               ▼
        ┌───────────────────────────────────────────────┐
        │ payments.new.retry.1   x-message-ttl = 1000мс │
        │ payments.new.retry.2   x-message-ttl = 5000мс │
        │ payments.new.retry.3   x-message-ttl = 25000мс│
        │   x-dead-letter-exchange     = payments       │
        │   x-dead-letter-routing-key  = payments.new   │
        └───────────────────────────────────────────────┘
                               │ TTL истёк → обратно в payments.new
                               ▼
                          (повторная обработка)

                     attempt >= 3 или неустранимая ошибка
                               ▼
                    ┌────────────────────────┐
                    │ exchange: payments.dlx │ (direct, durable)
                    └──────────┬─────────────┘
                               ▼
                    ┌────────────────────────┐
                    │ queue: payments.new.dlq│  (ручной разбор)
                    └────────────────────────┘
```

Задержки: **1с → 5с → 25с** (экспонента с основанием 5). Отдельная очередь на
каждый шаг, а не одна очередь с per-message TTL: в RabbitMQ TTL проверяется
только у головы очереди, поэтому сообщение с TTL 25с заблокировало бы стоящее
за ним сообщение с TTL 1с (head-of-line blocking).

Счётчик попыток — собственный заголовок `x-retry-count`, а не `x-death`:
он не зависит от того, каким путём сообщение вернулось в очередь.

Consumer работает с `AckPolicy.MANUAL`: сообщение подтверждается только после
того, как результат зафиксирован — либо обработка успешна, либо сообщение
успешно переопубликовано в retry/DLQ. Если процесс упадёт до `ack`, брокер
вернёт сообщение другому потребителю.

## 5. Классификация ошибок

Не всякая ошибка заслуживает трёх попыток.

| Ошибка | Класс | Поведение |
|---|---|---|
| Webhook вернул `5xx` | transient | retry |
| Таймаут / отказ соединения | transient | retry |
| Webhook вернул `429`, `408` | transient | retry |
| Webhook вернул прочие `4xx` | permanent | сразу DLQ |
| Платёж не найден в БД | permanent | сразу DLQ |
| Битый JSON в сообщении | permanent | сразу DLQ |
| Ошибка БД | transient | retry |

Три повтора к `404 Not Found` на стороне клиента не сделают его существующим —
это трата ресурсов и задержка полезных сообщений. `failed` статус платежа
(отказ шлюза) — **не ошибка обработки**: это нормальный бизнес-результат, о нём
так же уведомляют по webhook.

## 6. Consumer и идемпотентность

Один обработчик `payments.new` делает всё:

```
1. Загрузить платёж SELECT ... FOR UPDATE   (сериализация конкурентных доставок)
2. Если статус == pending:
       эмуляция шлюза: sleep(2..5с), 90% succeeded / 10% failed
       UPDATE status, processed_at, failure_reason
       COMMIT
   Иначе: шаг пропускается — платёж уже обработан
3. Если webhook_url задан и webhook_delivered_at IS NULL:
       POST webhook (HMAC-подпись, таймаут 5с)
       успех  → webhook_delivered_at = now(), COMMIT, ACK
       ошибка → webhook_attempts++, last_error, COMMIT, retry/DLQ
   Иначе: ACK
```

Разделение шагов 2 и 3 — суть идемпотентности. При повторной доставке (retry
доставки webhook, дубликат из outbox, возврат неподтверждённого сообщения)
**эмуляция шлюза не выполняется второй раз**: платёж уже не `pending`.
Повторяется только недоставленный webhook. Платёж не может быть обработан
дважды, даже если сообщение придёт десять раз.

`SELECT ... FOR UPDATE` защищает от гонки, когда два потребителя получили
дубликат одного события одновременно.

Webhook несёт заголовок `X-Webhook-Event-Id` (стабильный UUID, производный от
`payment_id`) — чтобы принимающая сторона тоже могла дедуплицировать, и
`X-Webhook-Signature` (HMAC-SHA256 тела) — чтобы могла аутентифицировать.

## 7. Идемпотентность API

`Idempotency-Key` — обязательный заголовок `POST /api/v1/payments`.

* Ключ уникален (`UNIQUE` в БД). Гонка двух одновременных запросов с одним
  ключом разрешается на уровне СУБД: проигравший ловит `IntegrityError`
  (`23505`) и читает победившую строку. Проверка «сначала SELECT, потом INSERT»
  здесь неверна — между ними есть окно.
* Вместе с ключом хранится `request_fingerprint` — SHA-256 канонизированного
  тела (отсортированные ключи, нормализованная сумма).
  * Тот же ключ + то же тело → `202` с существующим платежом и заголовком
    `Idempotent-Replay: true`. Ответ повторяется, побочный эффект — нет.
  * Тот же ключ + другое тело → `409 Conflict`. Молча вернуть старый платёж
    здесь опаснее, чем ошибка: клиент считает, что провёл новый платёж.

## 8. Аутентификация

Статический ключ в заголовке `X-API-Key` на всех эндпоинтах `/api/v1/*`.
Сравнение — `secrets.compare_digest` (защита от timing attack), не `==`.
`/health` и OpenAPI-схема открыты: health-проба не должна знать секретов.

Отсутствие ключа → `401`, неверный ключ → `401` (не `403`: не раскрываем, что
ключ существует).

## 9. Процессы

| Сервис | Роль | Масштабирование |
|---|---|---|
| `api` | HTTP, приём платежей | горизонтально, без состояния |
| `outbox-relay` | публикация событий из БД в брокер | горизонтально (`SKIP LOCKED`) |
| `consumer` | обработка платежей и webhook | горизонтально (prefetch=10) |
| `migrator` | `alembic upgrade head`, one-shot | — |
| `webhook-sink` | приёмник webhook для демонстрации | — |

Relay вынесен из API-процесса намеренно: публикация не должна конкурировать с
обслуживанием HTTP-запросов, а её остановка не должна ронять приём платежей.

Все три рабочих процесса переживают недоступность соседей: API работает при
мёртвом RabbitMQ (события копятся в outbox), consumer — при мёртвом webhook
(сообщения уходят в retry).

## 10. Тестирование

| Уровень | Что проверяет | Инфраструктура |
|---|---|---|
| unit | fingerprint, backoff, эмулятор шлюза, классификация ошибок, схемы | нет |
| integration (API) | эндпоинты, идемпотентность, гонка ключей, атомарность outbox | PostgreSQL |
| integration (relay) | публикация, `SKIP LOCKED`, backoff при сбое брокера | PostgreSQL |
| integration (consumer) | обработка, идемпотентность, retry, DLQ | PostgreSQL + `TestRabbitBroker` |
| e2e | обработка события через живой RabbitMQ (happy path) | весь compose |
| сквозной сценарий | все пункты ТЗ на поднятом стенде: `scripts/demo.sh` | весь compose |

`TestRabbitBroker` не эмулирует TTL и dead-lettering, поэтому маршрутизацию в
retry/DLQ на этом уровне проверяем по факту публикации в нужный обменник с
нужным ключом. Фактическое возвращение сообщения по TTL и попадание в DLQ на
живом RabbitMQ проверяет `scripts/demo.sh`: приёмник webhook управляемо отвечает
503 (успешная доставка после повторов), 404 (неустранимая ошибка → сразу DLQ) и
500 (исчерпание трёх попыток → DLQ, в режиме `--full`). Тот же скрипт проверяет
устойчивость к падению брокера: RabbitMQ останавливается, платёж всё равно
принимается, а после возврата брокера relay публикует накопленное.

Всё это запускается без локального Python: `make test` и `make lint` собирают
dev-стадию образа и гоняют pytest, ruff и mypy внутри контейнера, `make demo` —
сквозной сценарий. То же самое повторяет CI (`.github/workflows/ci.yml`).

## 11. Осознанно не реализовано

* **Планировщик просроченных платежей.** Платёж, зависший в `pending` из-за
  падения consumer'а между шагами, будет переобработан только после возврата
  сообщения брокером. Отдельный watchdog по `created_at` — избыточен для
  тестового.
* **Очистка `outbox_messages`.** В проде — партиционирование и удаление
  опубликованных старше N дней.
* **Ротация API-ключей, RBAC, rate limiting.** Вне рамок задания.
* **Валидация `webhook_url` против SSRF.** Consumer постит подписанное тело на
  произвольный URL из запроса — в проде туда нужен allow-list хостов и запрет
  внутренних адресов (метадата облака, `postgres:5432` и т.п.). Для тестового
  задания оставлено открытым сознательно.
* **Exactly-once доставка.** Недостижима; система строится на at-least-once
  плюс идемпотентность.
